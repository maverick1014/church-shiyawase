# 主恩堂（TOG / Tabernacle of Grace）教会管理系统 · 需求与用户故事

> 本文档由代码审计生成，严格对应仓库中**已实现**的行为。凡 API 支持但 UI 未暴露、或
> 尚未实现的能力，均在对应章节以「⚠ 缺口」标注，不做臆测。技术栈：Next.js 15（App
> Router）+ React 19 + Supabase，部署于 Cloudflare Workers（OpenNext）。全部界面为简体
> 中文、仅浅色主题、移动优先。API 为单一 catch-all 路由
> `apps/web/src/app/api/[...path]/route.ts`；鉴权为 HMAC 签名 Cookie
> （`apps/web/src/lib/server/auth.ts`）。

---

## 1. 系统概述

主恩堂教会管理系统是一套面向教牧团队的内部后台，用于牧养全流程管理：成员目录与个人档
案、小组编制与「铁三角」带领团队及每周出席、聚会点名、奉献记录与汇总、培训课程（场次 /
报名审核 / 核对名单）、以及「四十天一对一守望」门训接棒体系。系统以「登录账户 →
关联成员」的双层身份模型运作：**权限角色**（超级管理员 / 管理员 / 同工 / 只读）决定能在
应用中「做什么」，而成员在教会 / 小组中的**身份**（牧师 / 小组长 / … / 新成员）则由小组
管理页逐人分配、只读展示。所有写操作在服务端经统一鉴权闸门校验，客户端亦按会话角色隐藏
无权操作的入口；唯一的公开页面是带领者凭专属 token 访问的「每日守望填写表单」
（`/d/[token]`）。

## 2. 角色与权限矩阵

权限来源：服务端闸门 `route.ts`（权威）+ 客户端 `lib/perms.ts` 的 `can(role)`（仅用于隐
藏 / 禁用 UI）。矩阵反映**实际实现**：

| 能力 | 超级管理员 super_admin | 管理员 admin | 同工 coworker | 只读 readonly |
|---|:---:|:---:|:---:|:---:|
| 登录（账户须 active） | ✅ | ✅ | ✅ | ✅ |
| 查看数据（成员/小组/聚会/奉献/培训/门训/仪表盘） | ✅ | ✅ | ✅ | ✅ |
| 新增 · 编辑（牧养数据写操作，非 GET 且非 DELETE） | ✅ | ✅ | ✅ | ❌ |
| 删除（DELETE） | ✅ | ✅ | ❌ | ❌ |
| 账户管理（`/accounts*` 的**读与写**：列表、新建、编辑、删除、重设密码） | ✅ | ❌ | ❌ | ❌ |
| 查看教会资料与附加模块状态（`GET /church`、`GET /church/modules`） | ✅ | ✅ | ✅ | ✅ |
| 修改教会资料 / 主题颜色 / 开关附加模块（`/church*` 的**任意写操作**） | ✅ | ❌ | ❌ | ❌ |
| 自助修改我的密码（`/auth/password`，须验证当前密码） | ✅ | ✅ | ✅ | ✅ |
| 公开门训表单（`/d/[token]` 及 `/api/discipleship/form/*`，无需登录） | 公开（任何持 token 者） | 公开 | 公开 | 公开 |

服务端闸门要点（`route.ts` 顶部的 dispatch 闸门）：

- `r0 === 'auth'`、`discipleship/form/*`、`trainings/enroll/*` 与 **`GET /church`** 为公开路径，
  其余一律要求有效会话，否则 `401 未登录`。`GET /church` 公开是因为登录页与两个公开表单都要显示
  教会名称与教会主题色，且这些字段（name / short_name / description / logo_url +
  theme_preset / theme_rail / theme_brand）本身都不敏感；`/church` 的
  **写操作依旧仅 super_admin**。
- `accounts*` 的**任意方法（含 GET）** 仅 `super_admin`，否则 `403 仅超级管理员可管理登录账户`（读也受限，避免账户邮箱 / 角色 / 登录历史泄露）。
- `church*` 的**非 GET** 仅 `super_admin`，否则 `403`（改教会名称、换主题颜色或关掉一个模块，影响的是全教会）。
- 非 GET 时：`readonly` 一律 `403 只读账户无法修改`；`DELETE` 仅 `super_admin` / `admin`，否则 `403 当前角色无删除权限`。
- **模块启用（第三个访问维度，与角色、堂会并列）**：`church_modules` 记录本教会开启了哪些
  **附加模块**；代码侧的注册表（`packages/shared` 的 `OPTIONAL_MODULES`）说明每个模块拥有哪个
  导航入口与哪些 API 前缀。请求路径若属于一个**已关闭**的模块，服务端直接 `404 该模块未启用`
  ——含公开的带领者表单（模块关闭，其链接一并失效）。选 404 而非 403：模块关闭不是「你没有权限」，
  任何角色、任何堂会都无法访问，对本教会而言该功能并不存在。目前唯一的附加模块是
  `discipleship`（四十天守望）；`/auth*`、`/church*` 与所有核心路径永远不受此闸门影响。
- 密码：PBKDF2-HMAC-SHA256 加盐存储，最少 8 位；会话为 HMAC-SHA256 签名 Cookie（`tog_session`，HttpOnly / Secure / SameSite=Lax，7 天有效）。

## 3. 功能需求

> 约定：C=Create、R=Read、U=Update、D=Delete。「写」= 同工及以上；「删除」= 管理员及以上。
> 所有破坏性操作均须经共享 `useConfirm()`（`danger: true`）确认对话框，禁用原生
> `window.confirm`。

### 3.1 仪表盘 `/`（仪表盘）

- **R 只读概览**：KPI 卡（成员总数、在册成员、即将聚会、本月奉献 RM、门训进行中对数）、
  成员身份分布条形图、近八周奉献趋势 sparkline、即将到来的聚会（前 4）、门训进度关注（进
  度最低前 5）。
- 无任何写操作；所有登录角色可见。数据来自 `/members`、`/events`、`/donations`、
  `/discipleship/programs` 及**首个模块**的 `/overview`（仪表盘不带模块选择器，模块选择在
  `/discipleship`）。

### 3.2 成员目录 `/members` 与成员详情 `/members/[id]`（成员目录）

- **一个人 = 中文名 + 英文名**（迁移 0018）：`full_name` 是中文名，`english_name` 是英文名
  （可留空）。数据库对**这一对**建了唯一索引（忽略大小写与首尾空格，「没有英文名」本身也算
  一个值），所以同名的两位张伟必须用英文名区分；重复时 API 返回 **409** 并说明冲突，而不是
  抛出数据库错误。全应用凡是列出人的地方（表格、移动瓦片、点名表行、名单、配对行、账户表、
  成员 `Combobox`）都用共享的 `<MemberName />`：中文名在上，英文名在下一行、字号更小、
  颜色更淡；没有英文名就什么都不多画。
- **C 新增成员**（列表页「＋ 新增成员」，仅 `perms.write` 显示）：姓名（必填）、**英文名**、
  电话、状态（在册 / 停止聚会）、加入日期、邮箱、**照片**；`church_role` 固定为 `member`。
  身份 / 小组**不在此设定**（提示引导至小组管理）。照片用共享的 `<PhotoPicker />`：
  `accept="image/*"` 且**故意不加 `capture`**——系统弹窗会同时给出「拍照」与「相册」两个
  选择，加了 `capture` 反而只剩相机。选好即时预览，可移除；成员行写入成功后才走
  `POST /members/[id]/avatar` 上传（与详情页同一个接口，规则 G4）。
- **C 批量导入 `POST /members/import`**（列表页「导入」，仅 `perms.delete`＝超管 / 管理员）：
  接受 **.xlsx / .csv**，**两步**——先在浏览器解析并逐行预览「新增 / 更新 / 跳过及原因」，
  确认后才写入；有更新时经 `useConfirm({ danger: true })` 说明将覆盖多少位既有成员。
  **认人靠的是那一对姓名**（与 0018 唯一索引同一套比较：`tidy` 归一化 NFKC + 全角空格 +
  首尾空格，再小写比较，「没有英文名」＝空串），已存在的一对姓名 → **更新**，且**只更新
  文件里真正填了的列**（空格＝「这一栏没有要说的」，绝不清空教会已有的资料）。
  表头与枚举值在**三种语言**下都能识别（`lib/members-import.ts` 直接读三本字典比对，
  不另抄一份，单元测试守着不漂移）；模板由 `exportRows` 生成，列名即字典里的表头。
  逐行拒绝的情形：中文名为空、字段过长、**文件内重复同一对姓名**（指出重复的行号）、
  未知堂会 / 小组 / 教会身份 / 性别 / 状态、日期无法解读（只收年在前的 `YYYY-MM-DD`，
  `03/04/2026` 这种一律拒收）、邮箱 / 电话不成立、多堂会却没写堂会、越堂会写入。
  一行坏格不会连累整份文件；每条拒绝都带**电子表格里的行号**。
  服务端会**重新计算一遍同一份计划**（浏览器那份只是预览，权威在服务端，规则 G2），
  上限 300 行。
- **R 列表**：身份筛选 chip（含各身份计数 + 未分组）、姓名搜索（**中英文名任一命中**，忽略
  大小写；成员选择器 `comboboxFilter` 同样两个名字一起搜）、导出 Excel（`exportRows`，
  懒加载 SheetJS，含英文名一列）。桌面表格 / 移动列表瓦片两种呈现，点击进入详情。
- **R 详情**：头像、身份徽章、事实卡（邮箱 / 电话 / 性别 / 所属小组 / 状态 / 加入日期 /
  生日 / 家庭）、**个人培训档案**（来自 `/members/[id]/trainings`）、**四十天守望**配对列
  表（点击打开共享 `PairProgressModal` 进度弹窗）。
- **U 编辑资料**（详情页「编辑资料」，仅 `perms.write`）：姓名 / 英文名 / 电话 / 邮箱 /
  性别 / 生日 / 加入日期 / 状态 / 备注。身份与小组不在此改。
- **U 头像上传**（「上传头像 / 更换头像」，仅 `perms.write`）：`POST /members/[id]/avatar`
  （multipart），存入 Supabase `avatars` bucket。
- **D 删除成员**（详情页「删除」，仅 `perms.delete`）：确认对话框提示「培训、配对与出席记录将一并移除，且不可恢复」，删除后回到目录。
- **公开自助注册链接**（列表页「注册链接」，仅 `perms.write`）：复制 `/join` 的公开链接，
  用 `copyText` 并**无论成败都告知**。按钮放在成员管理而不是教会设置：这条链接产出的是
  **成员**，发链接的人正是看着这张名册的人；而教会设置只有超管进得去。
- ⚠ 说明：无法在 UI 中设置 `church_role = pastor`（牧师身份只能经数据库设定）。

### 3.3 小组管理 `/groups`（列表）+ `/groups/[id]`（详情）

- **`/groups` 列表**：所有小组的表格（组长、小组名称、组员人数、简介），可点击表头排序，点一行 →
  `/groups/[id]`。
- **C 新增小组**（「＋ 新增小组」，仅 `perms.write`）：名称（必填）、简介 / 聚会时间；保存后直接
  进入该小组的详情页。
- **`/groups/[id]` 详情 R**：左栏「小组资料 · 带领团队（铁三角）」，右栏「组员名单」；不再有小组间
  的 chip 切换（每个小组各自一个页面）。
- **U 编辑小组**（「保存设定」，仅 `perms.write`）：名称、简介。
- **D 删除小组**（「删除小组」，仅 `perms.delete`）：确认「组员将变为未分组」；删除后返回列表页。
- **组员名单（对成员的 U，仅 `perms.write`）**：
  - **添加成员入组**（**可输入搜索的 `Combobox`** + 「＋ 添加成员」）：`PATCH /members/[id]`
    设 `group_id` 并置身份为 `new_member`。
  - **移出小组**（「移除」）：确认对话框；清除 `group_id` 与 `group_position`。
  - **不再提供逐人身份下拉**——组员名单只列姓名 + 移除；核心成员 / 普通成员 / 新成员的身份改到
    该成员自己的档案页调整。
- **铁三角（本页唯一的身份指派入口）**：每个位置（小组长 / 副组长 / 实习组长）各一个
  **可输入搜索的 `Combobox`**（`size="sm"`），从本组组员中选人，仅 `perms.write` 可操作。
  - **每职位仅一人**：指派新领袖时，系统自动把原任者降为核心成员（`assignLeadership` 中
    auto-demote）。
  - 已移除「须先为核心成员方可晋升」的前置条件——任何组员都可直接被指派为三种组长之一。
- **出席点名卡（子模块 WeeklyAttendance）**：**一张表，两组列**——先是**该月主日**
  （会前 / 主日），再是**本组自己的聚会**（`group_meetings` / `group_attendance`）。
  表头有一行分组标题写明哪一组是哪一组，组长绝不会不知道自己勾的是主日还是本组聚会。
  卡内工具行＝左边年 / 月 `MonthPicker`、**右角导出按钮**（与各页 `PageBar` 的
  「左筛选、右动作」同一分法，G7a）；这一行属于**卡片自己**，不进页面的 `PageBar`。
  仍然没有「小组 / 会前 / 主日」分段切换——主日那半边不是第二个视图。
  - **主日那几列＝同一张点名表**（`GET /attendance/sheet?year&month&group_id=`）：
    列还是该月的主日（本组自己的聚会由本卡右半边负责，教会的聚会不归本组点），
    `group_id` 只收窄**行**（本组组员，与本卡右半边同一批人，因为一行就是一个人）。
    打勾走 `PUT /attendance/sheet`、原样回传同一个列 `key`，因此写进的是
    **「崇拜与祷告会」那一模一样的 `sunday_attendance` 行**（堂会取自成员自己的堂会，
    服务端读）。**一份记录，两个入口**：组长在自己的页面上点名，办公室读到的仍是同一个
    数字——一件事有第二个入口，只有这一种形状是安全的。
  - **堂会规则优先**：`group_id` 是对该小组的一次**读**，先过 `assertRowReadable`
    （与小组详情同一个守卫，G2），堂会账户不能借它看别堂的组员；`hallFilter` 照旧收窄。
  - 本组聚会的列＝该月本组聚会星期的日期 ＋ 该月已点过名的日期。
  - **U 勾选出席**（复选框，仅 `perms.write`）：主日格走上面那条 `PUT`；本组聚会格切换
    `present` / `absent`，首次勾选时惰性创建当周 `POST /groups/[id]/meetings`，再
    `POST /groups/meetings/[meetingId]/attendance`。只读用户复选框 `disabled`。
  - **U 整列全勾 / 全清（全员到齐）**：**每一子列**（每个主日的会前与主日各一个、每个周次
    一个）表头下方一个共享 `SheetTickAll`（不确定态复选框，仅 `perms.write`）——全勾则本次
    点击**清空整列**，否则**补满整列**；「一些人已勾」如实显示为 indeterminate。请求次数与
    「崇拜与祷告会」同一套逻辑（共享 `sheetColumnWrites`：按成员另一格现有的值分组，主日列
    最多两条请求），本组聚会那半边的 `records` 本来就是列表，整列与单格走同一条调用。
    清空会丢弃已有记录，故必经 `useConfirm({ danger: true })` 并写明将移除多少个勾；
    补满不需确认。
  - **表尾「到场人数」合计行**（共享 `SheetTotals`）：每一格（每个主日的会前 / 主日、每一周）
    在**自己那一列**下面写到场几个人。点名要回答的是「那一次来了多少人」，不是「这个人来过
    几次」，所以合计在**表尾**、按列读，而不是行尾多一列。
  - **R 导出**：`exportMatrix` 导出成员 ×（主日 ＋ 周次）矩阵，列与屏幕上完全一致，
    最后一行是各列到场人数合计。
- ⚠ 小提示：空态文案写「点『＋ 添加本周』」，实际按钮为「＋ 添加一周」（文案不一致，非功能缺陷）。会议 `note` 字段 API 支持但 UI 未采集。

### 3.4 崇拜与祷告会 `/events`（Services）

**每个主日本来就存在，不需要任何人去「创建主日」。** 页面上方是 `PageBar` 的年 / 月
筛选与「导出 / ＋ 新增聚会」两个动作，下面只有**一张卡：聚会点名表**。

- **一张表，两种列，按日期排序**（`lib/sheet.ts` 生成列，`GET /attendance/sheet`）：
  - **主日列**（`sunday_attendance`，迁移 0013）：该月每个主日，**每个主日两格**——
    「会前」（会前祷告）与「主日」（主日崇拜）。日期来自日历而不是数据，所以没人打过勾的
    主日照样有一列。
  - **聚会列**（`events` / `event_attendance`）：自行添加的聚会（例如 8 月 31 日晚祷告会）
    按日期插进当月主日之间，**只有一格「到场」**——一场聚会只有一件事要记，不会凭空多出
    一个「会前」。
  - **表尾「到场人数」合计行**（共享 `SheetTotals`，三张点名表同一个组件）：每一格
    （每个主日的会前 / 主日，每场聚会的到场）在**自己那一列的表尾**写出到场人数。
    点名表回答的是「那一次来了多少人」，而不是「这个人来过几次」，所以合计按列读，
    行尾不再有逐人次数列。数字直接取自表头「全员到齐」已经算过的那一份，不重算（G5）。
- **R**：`GET /attendance/sheet?year&month` → `{hall_id, columns[], rows[]}`。每列自带一个
  **不透明的 `key`**（`sunday:YYYY-MM-DD` / `meeting:<id>`），页面并不知道背后是两张表。
  可选 `&group_id=`：把**行**收窄成某个小组的组员（列仍是该月主日），供 `/groups/[id]` 的
  点名卡使用；先过 `assertRowReadable('groups', …)`，堂会规则照旧优先。写入路径一字未改，
  所以在小组页打的主日勾与本页是**同一行记录**。
- **U 打勾 / 取消**：`PUT /attendance/sheet`（把该列的 `key` 原样回传，由服务端决定写哪张
  表）。请求体带的是 **`member_ids` 列表**（`member_id` 为单数别名）：单格是「一个人的列表」，
  整列全勾是「全表成员的列表」，两者共用同一条路径、同一道门禁、同一条堂会规则，因此快捷方式
  不可能与单格行为漂移。取消勾选时**删除该行**，而不是存 false——「没有行」本来就等于「没有
  记录」（主日表上还有 CHECK 约束）。主日行的堂会取自**该成员自己的堂会**，客户端传的
  `hall_id` 一律忽略；列表里出现不存在的成员则整条请求 `400`，绝不半写。
- **U 整列全勾 / 全清（全员到齐）**：每一**子列**（主日的会前与主日各一个、聚会列一个）在
  表头日期下方各带一个共享 `SheetTickAll`（不确定态复选框，仅 `perms.write`）。全勾则点击
  **清空整列**，否则**补满整列**；页面按成员「另一格现有的值」分组下发，所以补满「主日」
  永远不会改写别人的「会前」——主日列最多两条请求，聚会列一条，绝不是每人一条。清空走
  `useConfirm({ danger: true })`，文案写明将删除多少个勾；补满不需确认。
- **堂会**：切换器选中某堂会时，成员名单与聚会列一并收窄（聚会另含 `hall_id is null` 的
  全堂开放场次）；**「全部堂会」时直接列出全部成员**（不再要求先选堂会，服务端也不再以
  400 拒绝）。
- **C 新增聚会 / U 编辑**（仅 `perms.write`）：只需**名称与日期**（外加堂会，堂会账户由
  服务端强制），不再有类型 / 地点 / 结束时间。编辑入口就是该聚会列表头上的名称按钮。
- **D 删除聚会**（编辑弹窗内，仅 `perms.delete`）：危险确认「及其出席记录」——删除会连同
  该列的所有勾一起消失（`event_attendance` 外键级联）。
- 表格很宽，所以它**在自己的卡内横向滚动**（与小组每周出席表一致），页面本体在 402px
  下永不横向滚动。
- **循环聚会已整体移除**（迁移 0015 删除 `recurring_events` 与 `events.recurring_id`）：
  日期本来就在日历上，点名表也不需要先有一行记录才能打勾，所以「提前排好一批聚会」这件事
  没有存在的理由；偶尔一次的祷告会直接新增即可。

### 3.5 奉献管理 `/donations`（奉献管理）

- **C 录入奉献**（「＋ 录入奉献」，仅 `perms.write`）：奉献人（可匿名）、日期、类别
  （十一奉献 / 主日奉献 / 建堂 / 宣教 / 感恩）、方式、金额（RM，须 > 0），币种固定 MYR。

- **U 编辑奉献**（行内「编辑」，仅 `perms.write`）：同录入字段。
- **D 删除奉献**（行内「删除」，仅 `perms.delete`）：确认对话框注明日期 / 奉献人 / 类别。

### 3.6 培训&活动 `/trainings` 与详情 `/trainings/[id]`（Trainings & Activities）

**一个目录，两种形态**（`trainings.kind`，迁移 0014，值为 `course` / `activity`）：

- **培训 course**：多场次、逐场点名（原样保留）。写作 `kind='course'`，界面上称「培训」。
- **活动 activity**：一次性的自由互动，如兄弟团爬山、姐妹团做蛋糕——**报名 + 点一次名**。
  活动的「那一次」不是新表：API 在创建活动时替它建**唯一一条 `training_sessions`**，
  只为给点名表一列可勾；**日期、时间与集合地点**就是记录自身的 `starts_on` / `ends_on`
  （同一天写两次）、`start_time` 与 `location`（迁移 0016），所以三者都只有一个编辑入口，
  那条 session 行的 `scheduled_at` / `location` 保持为空。`total_sessions` 由服务端强制为 1。
- **形态可互换**（0016）：培训 → 活动只保留**第一堂**，其余场次连同其出席记录一并删除，
  因此必须先经 `useConfirm({ danger: true })` 说明「删几堂、删几个勾」；活动 → 培训则把那
  唯一一堂直接当作第 1 堂，不删任何东西。不变量由服务端的 `ensureSingleSession` 保证。
- 两种形态共用同一套报名、点名与**公开自助报名链接** `/enroll/[id]`（按全名匹配成员）；
  公开接口按白名单返回 `kind`、日期/时间/地点、负责人及其联系方式、以及报名费三件套，
  让活动显示「日期 时间 · 地点」而不是「1 堂」，也让缴费者看得到该付多少、付去哪里。
- **不设形态筛选**：目录就是「这间教会现在在办什么」的一张单子，每张卡片自己带形态徽章，
  两种形态加起来也没多到需要藏起一半，所以那个下拉已移除。
- **界面上第一种形态叫「培训 / Training」**，不再叫「课程 / Course」——页面本来就叫
  培训&活动，多一个名字只会不一致；`kind` 在数据库与 API 上仍是 `course`，改名止于
  接口边界（G8）。

- **C 新增培训**（「＋ 新增培训」，仅 `perms.write`，`TrainingModal`）：名称（必填）、形态、
  **负责人 PIC**（纯文本）、**负责人联系方式**、场次数、起止日期、堂会、报名费、是否开放报名。
- **C 新增活动**（「＋ 新增活动」，仅 `perms.write`，同一个 `TrainingModal`）：名称（必填）、
  形态、**负责人 PIC + 联系方式**、**日期（单日）**、**开始时间**、**集合地点**、堂会、报名费、
  是否开放报名。
- **类别已移除**（0016）：它只是个显示标签，用在活动上什么也没描述，也没人按它筛选。
- **讲师/负责人改为纯文本**（0016）：培训常由外聘讲师带，uuid 指向 `members` 根本写不进去；
  真正需要的是一个**名字 + 一个可以打的号码**，所以是 `pic` / `pic_contact` 两列。
- **R 列表**：按「进行中 / 已结束·已截止」分组（结束依 `ends_on` 的**整个马来西亚日**已过，
  或 `is_enrollable=false`）；卡片带形态徽章与报名费徽章，
  「负责人 · 联系 · 场次/日期时间 · 地点」一行由 `trainingMeta`（`lib/labels.ts`）统一生成，
  目录卡、详情页与公开报名页共用同一份，永远不会各写各的（G4/G5）。
- **R 详情**：培训＝培训信息、场次列表、报名审核、核对名单矩阵；
  活动＝同一页面**不显示场次卡**（整行只剩报名审核），点名表只有一列「到场」。
  收费的项目多一张**报名费卡**（金额、付款方式文字、二维码），只在有费用时出现。
- **U 编辑**（详情「编辑培训 / 编辑活动」，仅 `perms.write`，`TrainingModal`）。
- **D 删除**（列表卡片或详情，仅 `perms.delete`）：确认「报名与出席记录将一并移除」。
- **场次**：
  - **C 加场次**（详情「＋ 加场次」，仅 `perms.write`）：第几课（自动取下一号）、标题、时间、地点。
  - ⚠ **缺口（G1）**：API 支持 `PATCH` / `DELETE /trainings/sessions/[id]`，但 UI **未提供场次的编辑 / 删除**入口。
- **报名**：
  - **C 加入报名**（「加入报名成员…」**可输入搜索的 `Combobox`**，仅 `perms.write`）：`POST /trainings/[id]/enroll`，
    默认状态 `pending`。
  - **U 通过报名**（「通过」，仅 `perms.write` 且状态为 `pending`）：`PATCH` 置
    `approved`。
  - ⚠ **缺口（G1）**：API 支持将报名改为 `in_progress` / `completed`（自动写
    `completed_at` 与 `progress=100`）/ `dropped`，及 `DELETE /trainings/enrollments/[id]`；
    但 UI **仅暴露 pending→approved**，无「拒绝 / 移除报名 / 标记完成 / 退出」入口。
  - **R 付款凭证**（收费项目，0016）：审核行里「通过」按钮旁就是「付款凭证」链接
    （新标签打开 `payment_slip_url`）；没有凭证的报名显示「无凭证」徽章。
    审核一笔收费报名的含义就是**有人真的打开凭证核对过钱到了**，所以链接放在做决定的那一行，
    而不是另一个页面。
- **核对名单（U 出席）**（点击方格切换 ✓，仅 `perms.write`）：
  `POST /trainings/sessions/[id]/attendance`；名单仅含 `approved` / `in_progress` /
  `completed` 报名。**表尾「到场人数」合计行**（共享 `SheetTotals`，标签横跨姓名 + 身份
  两格）：每一场次下面写该场到场几个人；名单为空时不画表尾。
  **R 导出名单**（`exportMatrix`，最后一行是各场次到场人数）。只读用户方格不可点。

**报名费（0016）**

- `trainings.fee` 为空或 0 ＝免费，下面所有东西都不出现；表单、公开页与服务端都问同一个问题
  （`hasFee` / `isPaid`）。
- 有费用则必须有 `payment_instructions`（纯文本：银行账号、TnG 号码、「当天交给司库」——
  **一列，不是每种付款方式一列**，因为教会一定会发明没人建模过的方式），
  外加可选的 `payment_qr_url`（上传的二维码图片，走成员头像/教会标志同一条上传通道）。
- 公开报名页在**必填的凭证上传框之上**依次显示金额、付款方式与二维码，并写明：
  先付款 → 上传收据 → 管理员核对后才通过。
- 凭证随报名**一次 multipart 提交**（同一条公开路径），不另开上传接口：
  只有在「开放报名 → 全名唯一匹配成员 → 尚未报名」全部通过之后才会写进 storage，
  所以这条全站唯一的免登录上传路径无法被当成免费网盘。
- 服务端校验（`route.ts`）：类型白名单 `image/jpeg|pjpeg|png|webp|gif|heic|heif` 与
  `application/pdf`（**故意不含 `image/svg+xml`**——SVG 会执行脚本，而桶是公开的）、
  ≤ 5MB、读字节之前先判断，全部以人话报 400。对象名用随机 uuid，URL 猜不出来。

### 3.7 四十天守望 `/discipleship`（门训接棒）

- **守望模块（modules，DB 仍称 `discipleship_programs`）**：模块定义名称、说明与总天数，
  配对经 `program_id` 挂在某个模块下。用户界面与三份词典一律称「模块 / module / modul」；
  数据库表名、字段名、API 路径（`/discipleship/programs`、`program_id`）保持不变。
  - **只建不改不删**。页面上曾有一个「模块」按钮 → 模块列表弹窗 → 逐行编辑 / 删除的管理器，
    那是把教会所说的「模块」（其实指 `/church` 上的**附加模块**开关）理解错了的产物，且它的
    删除会级联清掉该模块下的每一对配对与全部每日记录。整套管理器连同
    `PATCH`/`DELETE /discipleship/programs/:id` 两条路由一并移除——服务端现在直接 `404`，
    不是「界面藏起来」（G2：以服务端为准）。
  - **C（保留，仅空态）**：一个模块都没有时，页面提示新建并提供「＋ 新建模块」（只读账户则
    提示联系管理员）。表单字段：名称（必填）、说明、总天数（必填，整数 ≥ 1，前端校验 +
    服务端 `check (total_days >= 1)`）。保留这条路径的唯一理由：没有模块，整个四十天守望就
    没有东西可挂配对，而若连第一个都建不了，该页面就只能靠手写 SQL 恢复——这个坑已经踩过一次。
  - **选择器（保留）**：只有一个模块时页面无选择器；两个及以上时，`PageBar`
    **筛选区**出现模块下拉，切换即同时切换配对列表、接棒图、牧者总览与进度弹窗。不做持久化，
    默认第一个模块。
- **C 新增配对**（「＋ 新增配对」，仅 `perms.write`，须已有 programId）：选带领者 + 被带领
  者（已在配对中的被带领者不显示；不能自配）。系统按带领者已有配对自动串接 `parent_pair_id`
  形成接棒链。
- **R**：
  - 「培育链 · 接棒图」世代培育树（SVG 连接线），可按「在训 / 已出师 / 待开始」筛选，
    「在训」视图支持 **⛶ 全屏**。
  - 「牧者总览」表格 / 移动瓦片：配对（被带领 ← 带领）、进度条、状态，「进度」打开共享
    `PairProgressModal`，「🔗 表单」新开公开填写页。
- **U 进度**：仅通过公开门训表单 `/d/[token]`（见 §3.9）或 `PairProgressModal` 中复制 /
  打开表单链接来记录；⚠ **应用内无直接编辑每日进度的写控件**，进度录入完全依赖表单页
  `POST /discipleship/form/[token]/progress`（upsert）。
- **D 删除配对**（「删除」，仅 `perms.delete`）：确认「守望进度记录将一并移除」，
  `DELETE /discipleship/pairs/[id]`。
- ⚠ **缺口（G1）**：API 支持 `PATCH /discipleship/pairs/[id]`（如改 `status` 为
  `paused` / `completed`），但 UI **未提供配对的编辑 / 状态变更**入口。
- ⚠ **访问控制关注（G2）**：「🔗 表单」按钮与 `PairProgressModal` 的「复制链接 / 打开表单」
  对**所有登录角色（含只读）** 可见；公开表单端点无鉴权，因此只读用户可借总览中暴露的
  token 打开 `/d/[token]` 并提交每日进度，绕过「只读不可写」。见 §6。

### 3.8 用户管理 `/settings`（登录账户 · 权限角色，仅超级管理员）

- 导航项 `/settings` 带 `role: SuperAdmin` 门控；非超级管理员即使手动进入，页面主体显示
  「仅超级管理员可访问用户管理」，仅保留「修改我的密码」。服务端 `/accounts*` 读写均仅超级
  管理员。
- **C 新建账户**（「＋ 新建账户」）：关联成员（**可输入搜索的 `Combobox`**；已有账户者
  不在选项里）、登录邮箱、权限角色（默认同工）、初始密码（≥ 8 位）。`POST /accounts`
  （明文 `password` 服务端哈希为 `password_hash`）。「关联成员」「登录邮箱」两个标签不再
  带括号说明——已有账户者根本不出现在列表里，无须再解释。
- **R**：权限说明卡（四角色能力列表）、账户表格（关联成员、在组身份、权限角色、邮箱、状态、
  最近登录）。
- **U 编辑账户**（点账户进入详情「保存账户设置」）：邮箱、权限角色、堂会范围、账户状态
  （启用 / 停用）、
  两步验证开关（规划中）、界面语言、三类通知开关。详情页底部的「取消 / 保存账户设置」是共享的
  `.detail-footer`（`position: sticky; bottom: 0`，含 `env(safe-area-inset-bottom)`）——
  它**留在文档流里**，所以既钉在视口底部，又永远压不到最后一行内容。
  邮箱与堂会两条 💡 说明横幅已移除：字段名本身已经说清楚，两条横幅只是把一个七字段的表单
  拉长了一屏。
- **U 重设密码**（详情「重设该账户密码」）：超级管理员为任意账户直接重设（无需旧密码，
  ≥ 8 位）`POST /accounts/[id]/password`。
- **D 删除账户**（详情「删除账户」）：确认「其成员档案会保留」，`DELETE /accounts/[id]`。
- ⚠ **小缺口（G2 UX）**：`usePageChrome` 无条件设置顶栏动作，非超级管理员误入 `/settings`
  时顶栏仍显示「＋ 新建账户」按钮（点击无效，因新建弹窗只在超管分支渲染）。见 §6。

### 3.8b 教会设置 `/church`（教会资料 + 主题颜色 + 附加模块目录，仅超级管理员）

- 导航项 `/church` 位于「系统」分组、紧邻 `/settings`，同样带 `role: SuperAdmin` 门控；
  非超级管理员即使手动进入也会被重定向到 `/profile`（与 `/settings` 一致）。服务端
  `/church*` 的写操作同样仅超级管理员。
- **教会资料（R / U）**：名称、简称、简介、标志。标志走与成员头像完全相同的机制
  （`api.upload` → 公开存储桶 → 回写 `logo_url`），`POST /church/logo`；已有标志时可「移除
  标志」（`useConfirm` `danger` → `PATCH /church {logo_url: null}`）。教会记录是迁移 0012
  播种的**单行**，一个部署服务一间教会，因此**不提供新建 / 删除**（G1 的明示例外）。
- **主题颜色（R / U，迁移 0017）**：一套主题只有**两种颜色**——`theme_rail`（侧边栏）与
  `theme_brand`（品牌色）；其余色阶（`--brand-2`、`--brand-soft`、`--accent(-soft)` 以及侧边栏
  自身的浅色前景 `--rail-ink/-text/-muted/-faint/-dim`）一律在 `globals.css` 里以
  `color-mix()` 由这两色调配，**不入库**，因此永远不会与本色走样；`--good/--warn/--crit`
  与暖色中性色**不属于主题**（「缺席」不能因为教会选了红色就变成品牌色），`ROLE_TAG` 同理。
  - **预设**写在代码里（`packages/shared` 的 `THEME_PRESETS`：charcoal（今日配色，默认）、
    ink、forest、plum、amber），但**颜色与 preset key 一同入库**——日后改动某个预设的定义，
    不会悄悄改掉已选它的教会。
  - **自选**：两个 `<input type="color">` + 同一枚「对角切开的圆形」色卡实时预览
    （共享组件 `ThemeSwatch`，预设列表与预览用的是同一个，G4）；选中态除颜色外还有 ✓ 与加粗
    边框（不靠颜色单独表意）。
  - **服务端校验（G2）**：严格 `#rrggbb`（拒绝颜色名、缩写、`var(…)`、任何带 `;`/`}` 的串——
    这两个值会被写进 CSS 自定义属性），且**必须够深**：侧边栏 ≥ 8:1、品牌色 ≥ 4.5:1（对白）。
    浅色侧边栏不是「浅色主题」，而是看不见导航，因此直接拒绝而非半支持；预设按定义全部通过。
    数据库列另有同样的 `check` 约束兜底。
  - 主题属于**教会**而非账户：登录页与两个公开表单也照此上色，它们根本没有账户可读偏好。
    应用主题的唯一入口是 `lib/theme.ts` 的 `applyTheme`，由 `useChurchProfile` 调用（外壳与三个
    无外壳的公开页共用一条路径）；上次的配色缓存在 `localStorage`，由 `<head>` 内联的
    `THEME_BOOT_SCRIPT` 在**首帧之前**回填，因此只有某台设备的首次访问才可能闪一下默认配色。
  - 选择即保存（不销毁任何数据，一键可换回，故不需要 `useConfirm`）；保存后立即重绘侧边栏。
- **附加模块目录（R / U）**：注册表里每个可选模块一行——名称、一句话说明、开关。
  - 关闭一个模块会让全教会失去一整块功能，因此必经 `useConfirm({danger:true})`，文案同时说明
    **消失的是什么**（侧边栏入口、它的所有页面与链接）与**保留的是什么**（配对、每日进度、
    带领者表单链接一律不删，重开即恢复原状）。
  - 开启不销毁任何东西，因此不需要确认。
  - 切换后立即刷新侧边栏（`reloadModules`），无需整页重载。
- 目前唯一的附加模块是 `discipleship`（四十天守望）。核心页面（仪表盘、成员、小组、聚会、
  培训、账户、我的资料）**不可关闭**，也不在注册表内。

### 3.9 登录 / 退出 / 改密 / 公开表单

- **教会名称的边界**：登录页、`/d/[token]`、`/enroll/[id]`、`/join` 无会话，界面语言取默认（英文）；
  但**教会名称不是翻译而是数据**，三种语言都显示同一个名称，因此这几个页面各自请求公开的
  `GET /api/church` 并渲染 `church.name`（`form.privacy` / `join.privacy` 以 `{church}`
  占位符接收）。同一次请求也带回**教会主题色**，因此它们同样按教会的配色上色（`applyTheme`）。
  例外：`app/layout.tsx` 的 HTML `<title>` 与 `app/manifest.ts` 的 PWA 清单在**构建期**生成，
  没有请求也没有数据库连接，无法读取教会记录，故仍为按部署写死的字面量。
- **登录 `/login`**：邮箱 + 密码（含显示 / 隐藏切换），`POST /api/auth/login`。账户不存在或
  停用 → `401 账户不存在或已停用`；密码错误 → `401 邮箱或密码错误`。成功写会话 Cookie 并
  更新 `last_sign_in_at`，跳转 `/`。
- **会话守卫**：`AppShell` 挂载即 `GET /api/auth/me`，失败重定向 `/login`。
- **退出登录**（侧栏账户菜单「↩ 退出登录」）：经 `useConfirm`（`danger`）确认后
  `POST /api/auth/logout` 清除 Cookie，跳 `/login`。
- **修改我的密码**（侧栏「🔑 修改我的密码」或用户管理页按钮，`ChangePasswordModal`）：当前
  密码 + 新密码 + 确认；`POST /api/auth/password`，服务端校验旧密码、新密码 ≥ 8 位、两次一致。
- **公开门训表单 `/d/[token]`**：无需登录。展示带领者 → 被带领者、40 天进度格、进度条；只选
  第几天 ＋ 备注，提交 `POST /api/discipleship/form/[token]/progress`（upsert，`completed`
  恒为 `true`）。**没有「已完成 / 未完成」开关**：交这一天本身就是「这天做了」的意思，做了
  才会来填；那个开关只会让人填完一天、图上却仍显示什么都没发生。要把某天改回未完成，仍可从
  管理端 `PairProgressModal` 操作。日期选择器默认定位到下一个未填天。提交后显示成功态，
  可「再填一天」。
- **公开成员自助注册 `/join`**：无需登录，教会发一条链接出去，会众自己填。字段只有
  **中文名（必填）、英文名、电话、邮箱、性别、生日、堂会（多堂会时必选）、照片**。
  `POST /api/members/register` 与 `GET`（只回各堂会的 id + 名称，供表单渲染）是
  `/members` 之下**唯一**的公开路径，且只有这两个方法。
  服务端**不读** `church_role` / `group_id` / `group_position` / `status` / `notes`：
  字段按白名单读取，所以 body 里塞 `church_role: 'pastor'` 只会被忽略，每一位自助注册者
  都是一般成员。**同一对姓名已在名册上 → 更新其联系方式**（不改教会记下的姓名写法），
  页面据此显示「资料已更新」而不是「欢迎」；回应恒为 `{ status }` 一个词，两种结果同一形状，
  不带任何成员数据。照片与注册同一个 multipart 请求一起送（与付费报名的收据同一条规则：
  行没被接受之前，一个字节都不落存储），因此这条公开路径不能被当作文件寄存。

> 每条含 2–4 条可测**验收标准**，覆盖正常路径与访问控制负例。角色简称：超管 = 超级管理员。

### 用户管理（超管专属）

### 跨模块访问控制负例

**US-41：作为只读用户，任何写请求都会被服务端拒绝。**
- 客户端已隐藏绝大多数写按钮；即便构造 `POST/PATCH/DELETE`，服务端返回 `403 只读账户无法修改`。

**US-43：作为破坏性操作的执行者，我总会先看到确认对话框，以便防止误删。**
- 删除成员 / 小组 / 每周聚会 / 聚会 / 奉献 / 课程 / 配对 / 账户、移出小组、退出登录，均弹出
  `danger` 确认对话框；取消则不发生任何变更。无原生 `window.confirm`。

## 6. 审计发现（附录：CRUD 缺口与访问控制不一致）

按「安全 / 正确性 > CRUD 完整性 > 整洁度」排序：

1. **（G2）只读用户可经公开门训表单写入进度。** `/discipleship` 的「🔗 表单」按钮及
   `PairProgressModal` 的「复制链接 / 打开表单」对所有登录角色（含 readonly）可见；公开端点
   `/api/discipleship/form/[token]/*` 无鉴权。只读用户可借总览暴露的 `form_token` 打开
   `/d/[token]` 并提交每日进度，绕过「只读不可写」。失败场景：只读账户篡改门训进度而无审计。
   建议：对已登录会话访问表单端点时校验角色，或在只读会话下隐藏表单链接。

2. **（G2 · UX）非超管误入 `/settings` 时顶栏仍显示「＋ 新建账户」。** `usePageChrome` 无条件
   设置动作按钮；虽点击无效（弹窗仅在超管分支渲染），仍是不该出现的入口。建议：在
   `isSuperAdmin` 为假时不设置该动作。

3. **（G1）培训场次缺 U / D。** API 有 `PATCH` / `DELETE /trainings/sessions/[id]`，UI 无
   编辑 / 删除场次入口。加错场次只能改数据库。

4. **（G1）培训报名状态流转不完整。** API 支持 `in_progress` / `completed`（自动补
   `completed_at`、`progress=100`）/ `dropped` 及 `DELETE /trainings/enrollments/[id]`；UI 仅
   `pending→approved`，无拒绝 / 移除报名 / 标记完成 / 退出。

5. **（G1）门训配对缺 U。** API 有 `PATCH /discipleship/pairs/[id]`（可改 status 为 paused /
   completed），UI 无配对编辑 / 状态变更控件；配对状态实际只能停留在默认值。

6. **（G1 · 轻微）应用内无守望进度录入控件。** 进度只能经公开表单写入；牧者 / 管理员在应用
   内无法直接为某天打勾（须复制链接到表单页）。若这是刻意设计（仅带领者填表），应在 `docs/`
   明确记录。

7. **（轻微 · 文案）小组每周出席空态写「点『＋ 添加本周』」，实际按钮为「＋ 添加一周」。** 非功能
   缺陷，但违反 G8 用户可见字符串一致性。会议 `note` 字段 API 支持但 UI 从不采集。

8. **（轻微）成员牧师身份（church_role=pastor）无法在 UI 设定。** 新增仅置 `member`，编辑不含
   church_role；牧师身份只能经数据库写入。若为刻意（牧师身份由后台维护）应文档化。
