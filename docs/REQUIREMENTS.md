# 主恩堂（TOG / Tabernacle of Grace）教会管理系统 · 需求与用户故事

> 本文档由代码审计生成，严格对应仓库中**已实现**的行为。凡 API 支持但 UI 未暴露、或
> 尚未实现的能力，均在对应章节以「⚠ 缺口」标注，不做臆测。技术栈：Next.js 15（App
> Router）+ React 19 + Supabase，部署于 Cloudflare Workers（OpenNext）。全部界面为简体
> 中文、仅浅色主题、移动优先。API 为单一 catch-all 路由
> `apps/web/src/app/api/[...path]/route.ts`；鉴权为 HMAC 签名 Cookie
> （`apps/web/src/lib/server/auth.ts`）。

---

## 1. 系统概述

主恩堂教会管理系统是一套面向教牧团队的内部后台，用于牧养全流程管理：成员目录与个人档
案、小组编制与「铁三角」带领团队及每周出席、聚会点名、奉献记录与汇总、培训课程（场次 /
报名审核 / 核对名单）、以及「四十天一对一守望」门训接棒体系。系统以「登录账户 →
关联成员」的双层身份模型运作：**权限角色**（超级管理员 / 管理员 / 同工 / 只读）决定能在
应用中「做什么」，而成员在教会 / 小组中的**身份**（牧师 / 小组长 / … / 新成员）则由小组
管理页逐人分配、只读展示。所有写操作在服务端经统一鉴权闸门校验，客户端亦按会话角色隐藏
无权操作的入口；唯一的公开页面是带领者凭专属 token 访问的「每日守望填写表单」
（`/d/[token]`）。

## 2. 角色与权限矩阵

权限来源：服务端闸门 `route.ts`（权威）+ 客户端 `lib/perms.ts` 的 `can(role)`（仅用于隐
藏 / 禁用 UI）。矩阵反映**实际实现**：

| 能力 | 超级管理员 super_admin | 管理员 admin | 同工 coworker | 只读 readonly |
|---|:---:|:---:|:---:|:---:|
| 登录（账户须 active） | ✅ | ✅ | ✅ | ✅ |
| 查看数据（成员/小组/聚会/奉献/培训/门训/仪表盘） | ✅ | ✅ | ✅ | ✅ |
| 新增 · 编辑（牧养数据写操作，非 GET 且非 DELETE） | ✅ | ✅ | ✅ | ❌ |
| 删除（DELETE） | ✅ | ✅ | ❌ | ❌ |
| 账户管理（`/accounts*` 的**读与写**：列表、新建、编辑、删除、重设密码） | ✅ | ❌ | ❌ | ❌ |
| 查看教会资料与附加模块状态（`GET /church`、`GET /church/modules`） | ✅ | ✅ | ✅ | ✅ |
| 修改教会资料 / 开关附加模块（`/church*` 的**任意写操作**） | ✅ | ❌ | ❌ | ❌ |
| 自助修改我的密码（`/auth/password`，须验证当前密码） | ✅ | ✅ | ✅ | ✅ |
| 公开门训表单（`/d/[token]` 及 `/api/discipleship/form/*`，无需登录） | 公开（任何持 token 者） | 公开 | 公开 | 公开 |

服务端闸门要点（`route.ts` 顶部的 dispatch 闸门）：

- `r0 === 'auth'`、`discipleship/form/*`、`trainings/enroll/*` 与 **`GET /church`** 为公开路径，
  其余一律要求有效会话，否则 `401 未登录`。`GET /church` 公开是因为登录页与两个公开表单都要显示
  教会名称，且这四个字段（name / short_name / description / logo_url）本身不敏感；`/church` 的
  **写操作依旧仅 super_admin**。
- `accounts*` 的**任意方法（含 GET）** 仅 `super_admin`，否则 `403 仅超级管理员可管理登录账户`（读也受限，避免账户邮箱 / 角色 / 登录历史泄露）。
- `church*` 的**非 GET** 仅 `super_admin`，否则 `403`（改教会名称或关掉一个模块，影响的是全教会）。
- 非 GET 时：`readonly` 一律 `403 只读账户无法修改`；`DELETE` 仅 `super_admin` / `admin`，否则 `403 当前角色无删除权限`。
- **模块启用（第三个访问维度，与角色、堂会并列）**：`church_modules` 记录本教会开启了哪些
  **附加模块**；代码侧的注册表（`packages/shared` 的 `OPTIONAL_MODULES`）说明每个模块拥有哪个
  导航入口与哪些 API 前缀。请求路径若属于一个**已关闭**的模块，服务端直接 `404 该模块未启用`
  ——含公开的带领者表单（模块关闭，其链接一并失效）。选 404 而非 403：模块关闭不是「你没有权限」，
  任何角色、任何堂会都无法访问，对本教会而言该功能并不存在。目前唯一的附加模块是
  `discipleship`（四十天守望）；`/auth*`、`/church*` 与所有核心路径永远不受此闸门影响。
- 密码：PBKDF2-HMAC-SHA256 加盐存储，最少 8 位；会话为 HMAC-SHA256 签名 Cookie（`tog_session`，HttpOnly / Secure / SameSite=Lax，7 天有效）。

## 3. 功能需求

> 约定：C=Create、R=Read、U=Update、D=Delete。「写」= 同工及以上；「删除」= 管理员及以上。
> 所有破坏性操作均须经共享 `useConfirm()`（`danger: true`）确认对话框，禁用原生
> `window.confirm`。

### 3.1 仪表盘 `/`（仪表盘）

- **R 只读概览**：KPI 卡（成员总数、在册成员、即将聚会、本月奉献 RM、门训进行中对数）、
  成员身份分布条形图、近八周奉献趋势 sparkline、即将到来的聚会（前 4）、门训进度关注（进
  度最低前 5）。
- 无任何写操作；所有登录角色可见。数据来自 `/members`、`/events`、`/donations`、
  `/discipleship/programs` 及**首个模块**的 `/overview`（仪表盘不带模块选择器，模块选择在
  `/discipleship`）。

### 3.2 成员目录 `/members` 与成员详情 `/members/[id]`（成员目录）

- **C 新增成员**（列表页「＋ 新增成员」，仅 `perms.write` 显示）：姓名（必填）、电话、
  状态（在册 / 停止聚会）、加入日期、邮箱；`church_role` 固定为 `member`。身份 / 小组
  **不在此设定**（提示引导至小组管理）。
- **R 列表**：身份筛选 chip（含各身份计数 + 未分组）、姓名搜索、导出 Excel（`exportRows`，
  懒加载 SheetJS）。桌面表格 / 移动列表瓦片两种呈现，点击进入详情。
- **R 详情**：头像、身份徽章、事实卡（邮箱 / 电话 / 性别 / 所属小组 / 状态 / 加入日期 /
  生日 / 家庭）、**个人培训档案**（来自 `/members/[id]/trainings`）、**四十天守望**配对列
  表（点击打开共享 `PairProgressModal` 进度弹窗）。
- **U 编辑资料**（详情页「编辑资料」，仅 `perms.write`）：姓名 / 英文名 / 电话 / 邮箱 /
  性别 / 生日 / 加入日期 / 状态 / 备注。身份与小组不在此改。
- **U 头像上传**（「上传头像 / 更换头像」，仅 `perms.write`）：`POST /members/[id]/avatar`
  （multipart），存入 Supabase `avatars` bucket。
- **D 删除成员**（详情页「删除」，仅 `perms.delete`）：确认对话框提示「培训、配对与出席记录将一并移除，且不可恢复」，删除后回到目录。
- ⚠ 说明：无法在 UI 中设置 `church_role = pastor`（牧师身份只能经数据库设定）。

### 3.3 小组管理 `/groups`（列表）+ `/groups/[id]`（详情）

- **`/groups` 列表**：所有小组的表格（组长、小组名称、组员人数、简介），可点击表头排序，点一行 →
  `/groups/[id]`。
- **C 新增小组**（「＋ 新增小组」，仅 `perms.write`）：名称（必填）、简介 / 聚会时间；保存后直接
  进入该小组的详情页。
- **`/groups/[id]` 详情 R**：左栏「小组资料 · 带领团队（铁三角）」，右栏「组员名单」；不再有小组间
  的 chip 切换（每个小组各自一个页面）。
- **U 编辑小组**（「保存设定」，仅 `perms.write`）：名称、简介。
- **D 删除小组**（「删除小组」，仅 `perms.delete`）：确认「组员将变为未分组」；删除后返回列表页。
- **组员名单（对成员的 U，仅 `perms.write`）**：
  - **添加成员入组**（下拉 + 「＋ 添加成员」）：`PATCH /members/[id]` 设 `group_id` 并置身份为
    `new_member`。
  - **移出小组**（「移除」）：确认对话框；清除 `group_id` 与 `group_position`。
  - **不再提供逐人身份下拉**——组员名单只列姓名 + 移除；核心成员 / 普通成员 / 新成员的身份改到
    该成员自己的档案页调整。
- **铁三角（本页唯一的身份指派入口）**：每个位置（小组长 / 副组长 / 实习组长）各一个下拉，从本组
  组员中选人，仅 `perms.write` 可操作。
  - **每职位仅一人**：指派新领袖时，系统自动把原任者降为核心成员（`assignLeadership` 中
    auto-demote）。
  - 已移除「须先为核心成员方可晋升」的前置条件——任何组员都可直接被指派为三种组长之一。
- **出席点名卡（子模块 WeeklyAttendance）**：**只记本组自己的聚会**
  （`group_meetings` / `group_attendance`）。卡内工具行＝年 / 月 `MonthPicker` ＋
  **末尾的导出按钮**（与各页 `PageBar` 的先筛选后导出同一顺序，G7a）；这一行属于
  **卡片自己**，不进页面的 `PageBar`。已取消「小组 / 会前 / 主日」分段切换——成员的主日
  出席只在「崇拜与祷告会」的点名表上记一次，同一件事不再有两个入口。
  - 列＝该月本组聚会星期的日期 ＋ 该月已点过名的日期。
  - **U 勾选出席**（复选框，仅 `perms.write`）：切换 `present` / `absent`，首次勾选时
    惰性创建当周 `POST /groups/[id]/meetings`，再
    `POST /groups/meetings/[meetingId]/attendance`。只读用户复选框 `disabled`。
  - **R 导出**：`exportMatrix` 导出成员 × 周次矩阵 + 出席次数。
- ⚠ 小提示：空态文案写「点『＋ 添加本周』」，实际按钮为「＋ 添加一周」（文案不一致，非功能缺陷）。会议 `note` 字段 API 支持但 UI 未采集。

### 3.4 崇拜与祷告会 `/events`（Services）

**每个主日本来就存在，不需要任何人去「创建主日」。** 页面上方是 `PageBar` 的年 / 月
筛选与「导出 / ＋ 新增聚会」两个动作，下面只有**一张卡：聚会点名表**。

- **一张表，两种列，按日期排序**（`lib/sheet.ts` 生成列，`GET /attendance/sheet`）：
  - **主日列**（`sunday_attendance`，迁移 0013）：该月每个主日，**每个主日两格**——
    「会前」（会前祷告）与「主日」（主日崇拜）。日期来自日历而不是数据，所以没人打过勾的
    主日照样有一列。
  - **聚会列**（`events` / `event_attendance`）：自行添加的聚会（例如 8 月 31 日晚祷告会）
    按日期插进当月主日之间，**只有一格「到场」**——一场聚会只有一件事要记，不会凭空多出
    一个「会前」。
  - 行尾按本表实际出现的格子给出合计列（会前 / 主日 /（有聚会列时）到场）。
- **R**：`GET /attendance/sheet?year&month` → `{hall_id, columns[], rows[]}`。每列自带一个
  **不透明的 `key`**（`sunday:YYYY-MM-DD` / `meeting:<id>`），页面并不知道背后是两张表。
- **U 打勾 / 取消**：`PUT /attendance/sheet`（一格一次，把该列的 `key` 原样回传，由服务端
  决定写哪张表）。取消勾选时**删除该行**，而不是存 false——「没有行」本来就等于「没有
  记录」（主日表上还有 CHECK 约束）。主日行的堂会取自**该成员自己的堂会**，客户端传的
  `hall_id` 一律忽略。
- **堂会**：切换器选中某堂会时，成员名单与聚会列一并收窄（聚会另含 `hall_id is null` 的
  全堂开放场次）；**「全部堂会」时直接列出全部成员**（不再要求先选堂会，服务端也不再以
  400 拒绝）。
- **C 新增聚会 / U 编辑**（仅 `perms.write`）：只需**名称与日期**（外加堂会，堂会账户由
  服务端强制），不再有类型 / 地点 / 结束时间。编辑入口就是该聚会列表头上的名称按钮。
- **D 删除聚会**（编辑弹窗内，仅 `perms.delete`）：危险确认「及其出席记录」——删除会连同
  该列的所有勾一起消失（`event_attendance` 外键级联）。
- 表格很宽，所以它**在自己的卡内横向滚动**（与小组每周出席表一致），页面本体在 402px
  下永不横向滚动。
- **循环聚会已整体移除**（迁移 0015 删除 `recurring_events` 与 `events.recurring_id`）：
  日期本来就在日历上，点名表也不需要先有一行记录才能打勾，所以「提前排好一批聚会」这件事
  没有存在的理由；偶尔一次的祷告会直接新增即可。

### 3.5 奉献管理 `/donations`（奉献管理）

- **C 录入奉献**（「＋ 录入奉献」，仅 `perms.write`）：奉献人（可匿名）、日期、类别
  （十一奉献 / 主日奉献 / 建堂 / 宣教 / 感恩）、方式、金额（RM，须 > 0），币种固定 MYR。
- **R**：顶部四类汇总卡（来自 `/donations/summary`），明细表格（`table.stack` 移动堆叠），
  导出 Excel。
- **U 编辑奉献**（行内「编辑」，仅 `perms.write`）：同录入字段。
- **D 删除奉献**（行内「删除」，仅 `perms.delete`）：确认对话框注明日期 / 奉献人 / 类别。
- 操作列仅在 `perms.write || perms.delete` 时渲染。

### 3.6 培训&活动 `/trainings` 与详情 `/trainings/[id]`（Trainings & Activities）

**一个目录，两种形态**（`trainings.kind`，迁移 0014，值为 `course` / `activity`）：

- **课程 course**：多场次、逐场点名（原样保留）。
- **活动 activity**：一次性的自由互动，如兄弟团爬山、姐妹团做蛋糕——**报名 + 点一次名**。
  活动的「那一次」不是新表：API 在创建活动时替它建**唯一一条 `training_sessions`**，
  只为给点名表一列可勾；日期就是记录自身的 `starts_on` / `ends_on`（同一天写两次），
  所以日期只有一个编辑入口。`total_sessions` 由服务端强制为 1。
- 两种形态共用同一套报名、点名与**公开自助报名链接** `/enroll/[id]`（按全名匹配成员）；
  公开接口额外返回 `kind` 与 `starts_on`，让活动显示日期而不是「1 堂」。
- **筛选**：`PageBar` 筛选区一个下拉——「课程与活动 / 只看课程 / 只看活动」，
  值是**存储代码**而不是译名（G8）。

- **C 新增课程**（「＋ 新增课程」，仅 `perms.write`，`TrainingModal`）：名称（必填）、类别、
  场次数、讲师（成员）、起止日期、堂会、是否开放报名。
- **C 新增活动**（「＋ 新增活动」，仅 `perms.write`，同一个 `TrainingModal`）：名称（必填）、
  类别、**日期（单日）**、负责人、堂会、是否开放报名。`kind` 在创建时定下，编辑时不提供切换。
- **R 列表**：按「进行中 / 已结束·已截止」分组（结束依 `ends_on` 的**整个马来西亚日**已过，
  或 `is_enrollable=false`）；卡片带形态徽章，活动显示「负责人 · 日期」而非「讲师 · N 堂」。
- **R 详情**：课程＝课程信息、场次列表、报名审核、核对名单矩阵；
  活动＝同一页面**不显示场次卡**（整行只剩报名审核），点名表只有一列「到场」。
- **U 编辑**（详情「编辑课程 / 编辑活动」，仅 `perms.write`，`TrainingModal`）。
- **D 删除**（列表卡片或详情，仅 `perms.delete`）：确认「报名与出席记录将一并移除」。
- **场次**：
  - **C 加场次**（详情「＋ 加场次」，仅 `perms.write`）：第几课（自动取下一号）、标题、时间、地点。
  - ⚠ **缺口（G1）**：API 支持 `PATCH` / `DELETE /trainings/sessions/[id]`，但 UI **未提供场次的编辑 / 删除**入口。
- **报名**：
  - **C 加入报名**（「加入报名成员…」下拉，仅 `perms.write`）：`POST /trainings/[id]/enroll`，
    默认状态 `pending`。
  - **U 通过报名**（「通过」，仅 `perms.write` 且状态为 `pending`）：`PATCH` 置
    `approved`。
  - ⚠ **缺口（G1）**：API 支持将报名改为 `in_progress` / `completed`（自动写
    `completed_at` 与 `progress=100`）/ `dropped`，及 `DELETE /trainings/enrollments/[id]`；
    但 UI **仅暴露 pending→approved**，无「拒绝 / 移除报名 / 标记完成 / 退出」入口。
- **核对名单（U 出席）**（点击方格切换 ✓，仅 `perms.write`）：
  `POST /trainings/sessions/[id]/attendance`；名单仅含 `approved` / `in_progress` /
  `completed` 报名。**R 导出名单**（`exportMatrix`）。只读用户方格不可点。

### 3.7 四十天守望 `/discipleship`（门训接棒）

- **守望模块（modules，DB 仍称 `discipleship_programs`）**：模块定义名称、说明与总天数，
  配对经 `program_id` 挂在某个模块下。用户界面与三份词典一律称「模块 / module / modul」；
  数据库表名、字段名、API 路径（`/discipleship/programs`、`program_id`）保持不变。
  - **C / U / D**：页面动作区「模块」按钮打开模块列表弹窗（仅 `perms.write` 可见），内含
    「＋ 新建模块」与逐行「编辑」（`perms.write`）/「删除」（`perms.delete`）。表单字段：
    名称（必填）、说明、总天数（必填，整数 ≥ 1，前端校验 + 服务端 `check (total_days >= 1)`）。
    编辑已有配对的模块时，表单会以实际配对数提示「改天数会重算所有配对的完成百分比」。
    删除走共享 `useConfirm({ danger: true })`，并写明连带删除的配对数与最多多少天的每日记录
    （`discipleship_pairs.program_id` 与 `discipleship_progress.pair_id` 均为 `on delete cascade`）。
  - **选择器**：只有一个模块时页面与从前完全一致（无选择器）；两个及以上时，`PageBar`
    **筛选区**出现模块下拉，切换即同时切换配对列表、接棒图、牧者总览与进度弹窗。不做持久化，
    默认第一个模块。
  - **空态**：一个模块都没有时，页面提示新建模块并直接提供「＋ 新建模块」（只读账户则提示
    联系管理员）——删掉最后一个模块后仍可从 UI 恢复，不必再改数据库。
- **C 新增配对**（「＋ 新增配对」，仅 `perms.write`，须已有 programId）：选带领者 + 被带领
  者（已在配对中的被带领者不显示；不能自配）。系统按带领者已有配对自动串接 `parent_pair_id`
  形成接棒链。
- **R**：
  - 「培育链 · 接棒图」世代培育树（SVG 连接线），可按「在训 / 已出师 / 待开始」筛选，
    「在训」视图支持 **⛶ 全屏**。
  - 「牧者总览」表格 / 移动瓦片：配对（被带领 ← 带领）、进度条、状态，「进度」打开共享
    `PairProgressModal`，「🔗 表单」新开公开填写页。
- **U 进度**：仅通过公开门训表单 `/d/[token]`（见 §3.9）或 `PairProgressModal` 中复制 /
  打开表单链接来记录；⚠ **应用内无直接编辑每日进度的写控件**，进度录入完全依赖表单页
  `POST /discipleship/form/[token]/progress`（upsert）。
- **D 删除配对**（「删除」，仅 `perms.delete`）：确认「守望进度记录将一并移除」，
  `DELETE /discipleship/pairs/[id]`。
- ⚠ **缺口（G1）**：API 支持 `PATCH /discipleship/pairs/[id]`（如改 `status` 为
  `paused` / `completed`），但 UI **未提供配对的编辑 / 状态变更**入口。
- ⚠ **访问控制关注（G2）**：「🔗 表单」按钮与 `PairProgressModal` 的「复制链接 / 打开表单」
  对**所有登录角色（含只读）** 可见；公开表单端点无鉴权，因此只读用户可借总览中暴露的
  token 打开 `/d/[token]` 并提交每日进度，绕过「只读不可写」。见 §6。

### 3.8 用户管理 `/settings`（登录账户 · 权限角色，仅超级管理员）

- 导航项 `/settings` 带 `role: SuperAdmin` 门控；非超级管理员即使手动进入，页面主体显示
  「仅超级管理员可访问用户管理」，仅保留「修改我的密码」。服务端 `/accounts*` 读写均仅超级
  管理员。
- **C 新建账户**（「＋ 新建账户」）：关联成员（已有账户者不显示）、登录邮箱、权限角色
  （默认同工）、初始密码（≥ 8 位）。`POST /accounts`（明文 `password` 服务端哈希为
  `password_hash`）。
- **R**：权限说明卡（四角色能力列表）、账户表格（关联成员、在组身份、权限角色、邮箱、状态、
  最近登录）。
- **U 编辑账户**（点账户进入详情「保存账户设置」）：邮箱、权限角色、账户状态（启用 / 停用）、
  两步验证开关（规划中）、界面语言、三类通知开关。
- **U 重设密码**（详情「重设该账户密码」）：超级管理员为任意账户直接重设（无需旧密码，
  ≥ 8 位）`POST /accounts/[id]/password`。
- **D 删除账户**（详情「删除账户」）：确认「其成员档案会保留」，`DELETE /accounts/[id]`。
- ⚠ **小缺口（G2 UX）**：`usePageChrome` 无条件设置顶栏动作，非超级管理员误入 `/settings`
  时顶栏仍显示「＋ 新建账户」按钮（点击无效，因新建弹窗只在超管分支渲染）。见 §6。

### 3.8b 教会设置 `/church`（教会资料 + 附加模块目录，仅超级管理员）

- 导航项 `/church` 位于「系统」分组、紧邻 `/settings`，同样带 `role: SuperAdmin` 门控；
  非超级管理员即使手动进入也会被重定向到 `/profile`（与 `/settings` 一致）。服务端
  `/church*` 的写操作同样仅超级管理员。
- **教会资料（R / U）**：名称、简称、简介、标志。标志走与成员头像完全相同的机制
  （`api.upload` → 公开存储桶 → 回写 `logo_url`），`POST /church/logo`；已有标志时可「移除
  标志」（`useConfirm` `danger` → `PATCH /church {logo_url: null}`）。教会记录是迁移 0012
  播种的**单行**，一个部署服务一间教会，因此**不提供新建 / 删除**（G1 的明示例外）。
- **附加模块目录（R / U）**：注册表里每个可选模块一行——名称、一句话说明、开关。
  - 关闭一个模块会让全教会失去一整块功能，因此必经 `useConfirm({danger:true})`，文案同时说明
    **消失的是什么**（侧边栏入口、它的所有页面与链接）与**保留的是什么**（配对、每日进度、
    带领者表单链接一律不删，重开即恢复原状）。
  - 开启不销毁任何东西，因此不需要确认。
  - 切换后立即刷新侧边栏（`reloadModules`），无需整页重载。
- 目前唯一的附加模块是 `discipleship`（四十天守望）。核心页面（仪表盘、成员、小组、聚会、
  培训、账户、我的资料）**不可关闭**，也不在注册表内。

### 3.9 登录 / 退出 / 改密 / 公开门训表单

- **教会名称的边界**：登录页、`/d/[token]`、`/enroll/[id]` 无会话，界面语言取默认（英文）；
  但**教会名称不是翻译而是数据**，三种语言都显示同一个名称，因此这三个页面各自请求公开的
  `GET /api/church` 并渲染 `church.name`（`form.privacy` 以 `{church}` 占位符接收）。
  例外：`app/layout.tsx` 的 HTML `<title>` 与 `app/manifest.ts` 的 PWA 清单在**构建期**生成，
  没有请求也没有数据库连接，无法读取教会记录，故仍为按部署写死的字面量。
- **登录 `/login`**：邮箱 + 密码（含显示 / 隐藏切换），`POST /api/auth/login`。账户不存在或
  停用 → `401 账户不存在或已停用`；密码错误 → `401 邮箱或密码错误`。成功写会话 Cookie 并
  更新 `last_sign_in_at`，跳转 `/`。
- **会话守卫**：`AppShell` 挂载即 `GET /api/auth/me`，失败重定向 `/login`。
- **退出登录**（侧栏账户菜单「↩ 退出登录」）：经 `useConfirm`（`danger`）确认后
  `POST /api/auth/logout` 清除 Cookie，跳 `/login`。
- **修改我的密码**（侧栏「🔑 修改我的密码」或用户管理页按钮，`ChangePasswordModal`）：当前
  密码 + 新密码 + 确认；`POST /api/auth/password`，服务端校验旧密码、新密码 ≥ 8 位、两次一致。
- **公开门训表单 `/d/[token]`**：无需登录。展示带领者 → 被带领者、40 天进度格、进度条；选择
  第几天、已完成 / 未完成、备注，提交 `POST /api/discipleship/form/[token]/progress`（upsert）。
  日期选择器默认定位到下一个未填天。提交后显示成功态，可「再填一天」。

## 4. 用户故事

> 每条含 2–4 条可测**验收标准**，覆盖正常路径与访问控制负例。角色简称：超管 = 超级管理员。

### 认证与会话

**US-01：作为教牧同工，我想用邮箱密码登录，以便进入管理后台。**
- 在 `/login` 输入有效邮箱 + 密码，点「登录」后跳转到 `/`（仪表盘）。
- 邮箱或密码错误时，卡片内显示「⚠️ 邮箱或密码错误」，停留在登录页。
- 账户被停用（status≠active）时提示「账户不存在或已停用」。
- 密码框「👁 / 🙈」可切换明文显示。

**US-02：作为未登录访客，我访问任意后台页应被拦截，以便保障数据安全。**
- 直接访问 `/members` 等页，`GET /api/auth/me` 401 后浏览器重定向到 `/login`。
- 任意受保护 API 无有效 Cookie 时返回 `401 未登录`。

**US-03：作为已登录用户，我想退出登录，以便在共享设备上保护账户。**
- 点侧栏账户区 →「↩ 退出登录」，弹出危险确认对话框「确定要退出当前账户吗？」。
- 确认后 Cookie 清除并跳转 `/login`；取消则留在原页。

**US-04：作为任意角色用户，我想自助修改我的密码，以便定期更换。**
- 侧栏「🔑 修改我的密码」打开弹窗，需填当前密码、新密码、确认新密码。
- 新密码 < 8 位提示「新密码至少 8 位」；两次不一致提示「两次输入的新密码不一致」。
- 当前密码不正确时服务端返回「当前密码不正确」。
- 成功后 toast「密码已更新」。

### 仪表盘

**US-05：作为教牧同工，我想在仪表盘一览牧养全局，以便快速掌握现状。**
- `/` 顶部显示 5 张 KPI（成员总数 / 在册成员 / 即将聚会 / 本月奉献 RM / 门训进行中）。
- 显示成员身份分布条形图、近八周奉献趋势、即将聚会前 4、门训进度关注前 5。
- 只读用户同样可见全部图表，且页面无任何写按钮。

### 成员目录

**US-06：作为同工，我想新增成员，以便建立档案。**
- `/members` 右上「＋ 新增成员」→ 填姓名（必填）等 → 保存后 toast「已新增成员」，列表刷新。
- 未填姓名时提示「请填写姓名」。

**US-07：作为任意角色，我想搜索与筛选成员，以便快速定位。**
- 顶部身份 chip（含计数）与姓名搜索框可组合过滤；无结果显示「没有符合条件的成员。」。
- 「⬇ 导出 Excel」在有结果时可用，导出当前筛选行。

**US-08：作为同工，我想编辑成员资料与上传头像，以便保持信息准确。**
- 详情页「编辑资料」保存后 toast「已保存资料」；「上传头像 / 更换头像」成功后 toast「头像已更新」。
- 身份与所属小组字段不在编辑弹窗出现（提示引导至小组管理）。

**US-09：作为管理员，我想删除成员，以便清理无效档案。**
- 详情页「删除」→ 危险确认（提示记录不可恢复）→ 确认后 toast「已删除成员」并回到目录。

**US-10：作为只读用户，我在成员模块看不到任何写入口，以便避免误操作。**
- `/members` 无「＋ 新增成员」按钮；详情页无「编辑资料 / 上传头像 / 删除」。
- 只保留查看、搜索、导出。

**US-11：作为同工，我在成员详情看不到「删除」，因为删除属管理员及以上。**
- 同工详情页显示「编辑资料 / 上传头像」，但不显示「删除」按钮。

### 小组管理

**US-12：作为同工，我想创建小组并维护资料，以便组织牧养单元。**

  袖降为「核心成员」。

**US-14：作为同工，我想记录小组每周出席，以便追踪聚会情况。**

**US-35：作为带领者，我想通过专属链接每日填写守望进度，以便无需登录也能更新。**
- 打开 `/d/[token]` 显示带领 → 被带领与 40 天格；选第几天、已完成 / 未完成、备注，「提交今日进度」。
- 提交成功显示「已提交，感谢你的守望」，可「再填一天」；日期默认定位到下一个未填天。

**US-36：作为管理员，我想删除配对，以便纠正错误建立的关系。**
- 总览「删除」危险确认「其守望进度记录将一并移除」→ 成功 toast「已删除配对」。

**US-37：作为同工（非管理员），我在门训看不到「删除」。**
- 总览行 / 瓦片显示「进度 / 🔗 表单」但不显示「删除」。

**US-38：作为超管，我想在 UI 里新建 / 编辑 / 删除守望模块，让四十天守望不再依赖手写 SQL。**
- `/discipleship` 动作区「模块」→ 模块列表弹窗：「＋ 新建模块」、逐行「编辑」/「删除」。
- 删除前确认框写明会连带删除多少对配对与最多多少天的每日记录；删光后空态引导重新新建。
- 仍是缺口：配对状态（暂停 / 完成）无 UI 变更控件（见「已知缺口」第 6 条）。

### 用户管理（超管专属）

**US-39：作为超级管理员，我想新建、编辑、停用与删除登录账户，以便管理团队访问。**
- `/settings`「＋ 新建账户」关联成员 + 邮箱 + 角色 + 初始密码（≥ 8 位）→ toast「已新建账户」。
- 账户详情可改邮箱 / 权限角色 / 启停 / 语言 / 通知，「保存账户设置」toast「已保存账户设置」。
- 「重设该账户密码」（≥ 8 位，无需旧密码）成功 toast「已为 X 重设密码」。
- 「删除账户」危险确认「其成员档案会保留」→ toast「已删除账户」。

**US-40：作为非超管用户，我不能访问用户管理，以便账户信息不外泄。**
- 侧栏不显示「用户管理」导航项。
- 手动进入 `/settings` 显示「仅超级管理员可访问用户管理」，仅保留「修改我的密码」。
- 服务端对 `/accounts*`（含 GET）一律 `403 仅超级管理员可管理登录账户`。

### 跨模块访问控制负例

**US-41：作为只读用户，任何写请求都会被服务端拒绝。**
- 客户端已隐藏绝大多数写按钮；即便构造 `POST/PATCH/DELETE`，服务端返回 `403 只读账户无法修改`。

**US-42：作为同工，我的删除请求被服务端拒绝。**
- 同工发起任意 `DELETE` 返回 `403 当前角色无删除权限`；对应 UI 删除按钮也不渲染。

**US-43：作为破坏性操作的执行者，我总会先看到确认对话框，以便防止误删。**
- 删除成员 / 小组 / 每周聚会 / 聚会 / 奉献 / 课程 / 配对 / 账户、移出小组、退出登录，均弹出
  `danger` 确认对话框；取消则不发生任何变更。无原生 `window.confirm`。

## 6. 审计发现（附录：CRUD 缺口与访问控制不一致）

按「安全 / 正确性 > CRUD 完整性 > 整洁度」排序：

1. **（G2）只读用户可经公开门训表单写入进度。** `/discipleship` 的「🔗 表单」按钮及
   `PairProgressModal` 的「复制链接 / 打开表单」对所有登录角色（含 readonly）可见；公开端点
   `/api/discipleship/form/[token]/*` 无鉴权。只读用户可借总览暴露的 `form_token` 打开
   `/d/[token]` 并提交每日进度，绕过「只读不可写」。失败场景：只读账户篡改门训进度而无审计。
   建议：对已登录会话访问表单端点时校验角色，或在只读会话下隐藏表单链接。

2. **（G2 · UX）非超管误入 `/settings` 时顶栏仍显示「＋ 新建账户」。** `usePageChrome` 无条件
   设置动作按钮；虽点击无效（弹窗仅在超管分支渲染），仍是不该出现的入口。建议：在
   `isSuperAdmin` 为假时不设置该动作。

3. **（G1）培训场次缺 U / D。** API 有 `PATCH` / `DELETE /trainings/sessions/[id]`，UI 无
   编辑 / 删除场次入口。加错场次只能改数据库。

4. **（G1）培训报名状态流转不完整。** API 支持 `in_progress` / `completed`（自动补
   `completed_at`、`progress=100`）/ `dropped` 及 `DELETE /trainings/enrollments/[id]`；UI 仅
   `pending→approved`，无拒绝 / 移除报名 / 标记完成 / 退出。

5. **（G1）门训配对缺 U。** API 有 `PATCH /discipleship/pairs/[id]`（可改 status 为 paused /
   completed），UI 无配对编辑 / 状态变更控件；配对状态实际只能停留在默认值。

6. **（G1 · 轻微）应用内无守望进度录入控件。** 进度只能经公开表单写入；牧者 / 管理员在应用
   内无法直接为某天打勾（须复制链接到表单页）。若这是刻意设计（仅带领者填表），应在 `docs/`
   明确记录。

7. **（轻微 · 文案）小组每周出席空态写「点『＋ 添加本周』」，实际按钮为「＋ 添加一周」。** 非功能
   缺陷，但违反 G8 用户可见字符串一致性。会议 `note` 字段 API 支持但 UI 从不采集。

8. **（轻微）成员牧师身份（church_role=pastor）无法在 UI 设定。** 新增仅置 `member`，编辑不含
   church_role；牧师身份只能经数据库写入。若为刻意（牧师身份由后台维护）应文档化。
